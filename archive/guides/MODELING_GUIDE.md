# 建模流程指南（MODELING\_GUIDE）

> 給未來的自己，也給其他建模專案的 AI。內容來自 ProceduralBuilding\_v2 的實作經驗（2026-10）。 專案細節看 [blender/KIT_SPEC.md](../../blender/KIT_SPEC.md)（外牆零件）和 [INTERIOR_SPEC.md](../../INTERIOR_SPEC.md)（室內）；這份只講「怎麼做 事」。 Token 數是相對估計，不是量測值；以「做一個零件」為 1。
>
> **換算**：1 單位 ≈ 5 次操作（讀一個檔、改一個檔、跑一個指令、看一張截圖，各算一次）。老虎窗第一輪實際約 25 次操作、約 4 張截圖、改 7 個檔案，約等於 5 單位。這個次數是事後回想的粗估，不是量測；要真實的 token，請在 Claude Code 用 `/cost` 比較每個階段前後。
>
> **次數會低估的原因**：每次操作背後還有思考與說明，工具回傳的內容也會被讀進來（截圖與大檔案最重），對話越長每一輪越貴；次數只算動作的數量，沒算每個動作的大小。請把它當作「排出哪個步驟比較重」，不要換算成實際花費。

**涵蓋的內容索引**

1.  **照片與 3D 檔的取用差異**：照片只取比例、款式、顏色；3D 檔能量尺寸，但有單位、面數、授權的問題。照片比 3D 檔省，也 講了怎麼給照片最省。
2.  **三種建模路線**：Blender Python 背景建模、網頁端程式建模、著色器畫圖樣，各自的適用時機。
3.  **材質與貼圖流程**：自製貼圖、三平面投影、只調數值的改款、室內戳記。
4.  **AO**：什麼時候用、什麼時候要重烘焙（連補一塊缺口也要）、什麼時候不用，以及「烘焙不花 token」。
5.  **三種東西的比較表**：建築外觀約 3 到 5、家具約 1 到 2、路樹約 1（以一個零件為 1）。這是我的粗估，不是量測值，文件裡 也有註明。
6.  **零件總覽**：用途、和 Blender 預覽圖互補、建議新專案一開始就做。
7.  **我修改模型時怎麼運作**：先讀不重寫、改在源頭、小步驗證、全組合檢查、文件同步、推送前先問。
8.  **model 與 effort 對照表**，以及省 token 的做法。
9.  **新專案的 prompt 範本**：先要求我回答五個問題（怎麼拆零件、尺寸放哪、AO 怎麼集中、怎麼驗證、建議等級），確認後才動 工，附工作規則。
10.  **你可能不知道的事**：剖切原理、繪製次數比三角形數重要、光源數量要固定、細線遠處會消失等。
11.  **檔案地圖**。

## 1\. 照片與 3D 檔，我怎麼取用

|  | 參考照片 | 現成 3D 檔（GLB 等） |
| --- | --- | --- |
| 我取得什麼 | 比例、款式、顏色、細節的位置 | 精確尺寸、節點結構、三角形數、材質數 |
| 取不到什麼 | 精確尺寸（要猜，或你直接寫公分） | 授權、設計意圖、網格品質 |
| 取用方式 | 看圖，用程式從基本形狀重做 | 先用程式讀 JSON 頭量尺寸，再決定要不要用 |
| 主要風險 | 看不到的面、被遮住的細節 | 單位（常是毫米）、面數太多、網格不封閉、授權 |
| 本專案的做法 | 全部採用 | 只當尺寸參考，**沒有放進專案**（授權未確認、面數太高） |

-   **照片比 3D 檔更省**：3D 檔要處理節點（本專案的床 146 個、書櫃 212 個）、單位、簡化；照片直接重做，三角形數從設計就控 制住。
-   **給照片的建議**：一件東西 1 到 2 張，最好有正面或側面；在圖上畫線標出要改的地方（用紅線標屋頂、藍線標窗格，一次就 對）；知道尺寸就直接寫公分。
-   **同一張圖看越多次越貴**：每看一次圖就花一次 token，截圖驗證也一樣。

## 2\. 三種建模路線

| 路線 | 做法 | 適合 | 不適合 |
| --- | --- | --- | --- |
| **A. Blender Python 背景建模** | 腳本在無介面的 Blender 裡建零件，匯出 GLB 和 manifest（`blender/kitlib/`、`npm run kit`） | 要重複使用很多次的零件（窗、陽台、老虎窗）；要 UV、法線、AO | 只出現一兩次的東西 |
| **B. 網頁端程式建模** | 在 TypeScript 裡直接生成三角形，依材質合併成幾個網格（`stairs.ts`、`furniture.ts`、`rooms3d.ts`） | 一棟只有一個或幾個的東西（樓梯、宴會廳桌椅、室內牆）；尺寸要跟著平面變 | 數量很多、重複的零件 |
| **C. 著色器畫圖樣** | 在 GLSL 裡用座標畫（人字拼地板、地毯、書背、石縫） | 平面的圖樣；不想管貼圖檔 | 立體的造型 |

-   **A 和 B 的分界**：看數量。重複出現就用 A（用實例化，一個零件不論放幾百次都只有一次繪製）；一棟只有一個就用 B（省掉匯 出載入流程）。
-   **A 的限制**：改了零件就要重新建置 kit，而且常常要重烘焙 AO（見第 4 節），所以先把形狀想好再動。
-   **C 的好處**：不用貼圖檔、不用烘焙，改一個數字就看得到；缺點是只能畫平面圖樣。

## 3\. 材質與貼圖流程

1.  **自製貼圖**：`blender/bake.py` 用 Blender 節點（噪聲、Voronoi，用 4D 座標讓貼圖無縫）烘焙出石材、灰泥、鋅板等的顏色 圖（1024²）與粗糙度加高度圖（512²），存到 `public/assets/tex/`。
2.  **網頁端著色**：`src/materials.ts` 用 `onBeforeCompile` 把這些貼圖用世界座標的三平面投影蓋上去（同一個零件放多次也不 會重複、相鄰零件沒有接縫），再疊上石縫、鋅板的接縫等圖樣。
3.  **每棟建築自己的顏色**：用實例顏色（instance color）調，不複製材質。
4.  **只調顏色與數值的改款**：例如「巴黎淺色石灰岩」只改著色器的數值（`FACADE_LOOKS`），不動零件、不烘焙。
5.  **室內材質**：在 `finishes.ts` 的著色器裡畫（地板、牆面、地毯、書背），每個頂點帶一組「戳記」（花樣、兩個顏色、地板 與天花高度），所有房間合成一個網格。
6.  **材質名稱就是介面**：Blender 的材質名稱要跟 `materials.ts` 的名稱一致，換名字等於換材質。

## 4\. AO（環境光遮蔽）什麼時候要用，什麼時候要重烘焙

-   **是什麼**：角落、縫隙的柔和陰影，烘焙成一張圖（`kit_ao.jpg`），零件的第二組 UV（UV1）指向圖上自己的位置。
-   **為什麼用**：即時算 AO 很貴；烘焙一次，網頁端只是多採一張圖。窗框、飛簷、陽台底下的陰影都靠它。
-   **要重烘焙（`npm run ao`，約 10 分鐘）**：
    -   新增零件、**改變零件的形狀**（連補一塊缺口也要，因為展開圖會變）。
    -   零件的數量變了（圖集的排列整個會變）。
-   **不用重烘焙**：只改材質顏色、貼圖、著色器、擺放規則、尺寸常數以外的程式。
-   **AO 只對 kit 零件有效**：網頁端生成的東西（屋頂、室內、樓梯、家具）沒有 UV1，用不掛 AO 的材質。
-   **烘焙不花 token**：它在你的電腦上跑，只有「等它完成後建置、commit」那一步才算。要省就把形狀改動集中，**一次烘焙**。

## 5\. 三種東西的流程比較

|  | 建築外觀（kit 零件） | 簡易家具 | 路樹、人行道 |
| --- | --- | --- | --- |
| 路線 | A（Blender 腳本） | B（程式建模） | B + 著色器（canvas 畫圖樣） |
| 尺寸從哪來 | `kit_dims.json`（所有人共用，只改這裡） | 程式裡的常數，依房間大小調整 | `kit_dims.json` 的 `street` |
| 要不要 AO | 要 | 不要 | 不要 |
| 要不要匯出 | 要（GLB、manifest） | 不要 | 不要 |
| 驗證 | 零件總覽 + 截圖 + 尺寸檢查 | 剖開截圖 | 截圖 |
| 改動的連鎖影響 | 大：排列規則、室內開口、AO、manifest | 小：只有家具自己 | 小 |
| **操作次數（約）** | **約 15 到 25 次**（形狀推敲、對齊既有尺寸、重烘焙後再驗證） | **約 5 到 10 次**（一個零件組，重複用 helper 後更便宜） | **約 5 次**（沿用 v1 的程式，只調尺寸與配色） |

-   **最貴的是改動會連鎖的**：外牆零件一改，室內的窗洞（manifest 開口輪廓）、閣樓的斜面開洞、點選的範圍都可能要跟著改。這 是「先問再做」的原因。
-   **第二次比第一次便宜**：寫過一次 helper（車削、方塊、桿件），之後每個新家具只是組合。

## 6\. 零件總覽（開發者的好工具）

-   GUI 打開「零件總覽」：把 kit 的每個零件排成兩排，上面標名字（`R_mansard dormer_studio`），低的在前、高的在後；背後是可 切換的燈光氛圍。
-   **用途**：
    -   新零件做完，**不用組成整棟建築**就能檢查形狀、材質、尺寸。
    -   看缺面、穿模、比例（上一個老虎窗的缺口就是在這裡看出來的）。
    -   在不同光線下看材質。
-   **和 Blender 的 `kit_preview.jpg` 互補**：預覽圖是 Blender 渲染的，總覽是網頁上的真實材質。
-   做新專案時，**一開始就做一個零件總覽頁**，之後每個階段的驗證都便宜。

## 7\. 我修改模型時怎麼運作

1.  **先讀，不重寫**：讀規格、讀要改的程式與它周圍，確認尺寸常數在哪（`kit_dims.json`）。
2.  **改在源頭**：零件由腳本產生，不手改 `.blend`；尺寸只改 `kit_dims.json`。
3.  **小步驗證**：改完立刻 `tsc` 型別檢查，再用截圖看（瀏覽器腳本設定相機、剖切位置、拍照）。
4.  **特別驗證容易出錯的地方**：兩端的狀態（滑桿最左最右）、不同建築類型、手機寬度、夜景。
5.  **全組合檢查**：改了平面規則，就跑 `planCheckAll`（本專案約 2.6 萬種組合），避免只在預設建築上正確。
6.  **文件同步**：規格、決策紀錄、`CLAUDE.md` 一起更新，下一個 session 才接得起來。
7.  **commit 小而完整**：一個功能一個 commit，**推送前先問**。
8.  **先問 model 與 effort**：每個新階段開始前，我會建議等級，等你切換後才動工（見第 8 節）。
9.  **做錯就說**：截圖發現不對，就說「第一版太灰、太平」並修正，不假裝完成。

## 8\. model 與 effort 怎麼選（以 Claude 為例）

### 8.1 一般原則

| 工作 | 建議 |
|---|---|
| 調顏色、改字、改預設值、加按鈕 | Sonnet、low 到 medium |
| 照照片做新零件、套用現有規則、截圖調整 | Sonnet、high |
| 要改規則、狀態交會、跨多個檔案的連鎖（剖切、點選、平面配置） | Opus、high |
| 全新的大階段、新的演算法 | Opus、max |
| 寫文件、整理已完成的事 | Sonnet、medium |

-   **做不到時才升級**：先用便宜的，同一個問題修兩次還對不上，再換 Opus。
-   **品質取決於規格，不是 model**：模型看起來太粗，是因為我沒用曲線，不是 model 不夠強；說清楚要「車削的腳」、「弧形椅背」，Sonnet 一樣做得到。

### 8.2 本專案各項目實際怎麼選

「實際」是當時你切換的等級；「—」代表我沒有記錄，只能給建議。

| 項目 | 做了什麼 | 實際 | 為什麼 |
|---|---|---|---|
| **樓梯**（I3） | 圓角環繞樓梯：踏步尺寸、平台、欄杆；順便改平面規則 | Opus、max | 樓梯間大小、門的位置、平面全組合都連動，要推理；改完要跑 2.6 萬種組合 |
| **窗戶：點選個別設定** | 點窗戶改細節、套用整欄整排、即時調整 | Opus、high | 零件要帶標記、射線判斷、狀態保存，牽涉 5 個檔案 |
| **窗戶：宴會廳高窗**（I4） | 6 個新零件、排列規則、窗後房間依平面挑 | 建議 Sonnet 或 Opus、medium | 有規格可照做，主要是接線；要重烘焙 AO |
| **屋頂：老虎窗大玻璃款** | 新零件、閣樓內牆開洞、點選 | Opus、high | 要對齊屋頂坡面與閣樓內牆；詳見 8.3 的範例 |
| **屋頂：補缺口、修穿模** | 側牆補一塊、圓窗通道縮小 | Sonnet、high | 找座標對不上的地方，不需要新規則 |
| **裝飾造型**（窗套、窗楣、陽台托架…） | 外牆零件的細節 | —（建議 Sonnet、high） | 照圖用程式建模，有現成的剖面函式可用 |
| **外牆材質**（巴黎淺色石灰岩） | 只調著色器數值 | Sonnet、medium | 只改顏色與數值，要比照片來回調色 |
| **室內地板與牆面** | 人字拼、六角磚、護牆板、壁紙 | —（建議 high） | 著色器要自己寫，圖樣要看起來對 |
| **人行道、路樹** | 從 v1 移植，換成公尺、巴黎風、跟著輪廓 | Sonnet、medium；跟輪廓那次 Sonnet、high | 沿用現成程式；輪廓幾何容易方向反，所以升到 high |
| **家具**（宴會廳桌椅、書房） | 車削的腳、書櫃、檯燈、燈光池 | Sonnet、high | 照圖組形狀，細節取決於我描述了多少 |
| **剖切、反向、顯示內部按鈕** | 切面、材質切換、介面 | 反向 Sonnet、medium；顯示內部 Opus | 反向規則簡單；兩端的狀態與按鈕分工要仔細 |
| **文件**（規格、這份指南） | 整理已完成的事 | Sonnet、medium | 沒有新的推理 |

-   **看得出的規律**：只要是「改規則」或「狀態會互相影響」（樓梯、點選、剖切），就用 Opus；只要是「照圖做一個東西」（家具、裝飾、人行道），Sonnet 的 high 就夠。
-   **effort 看「要檢查的地方有多少」**：窗戶、屋頂的改動要檢查室內開口、AO、點選，所以 high；調顏色只看畫面，所以 medium。

### 8.3 範例：做屋頂的老虎窗，每一步怎麼走

這次「閣樓書房的大玻璃老虎窗」從頭到尾的流程，以及每一步用什麼（以操作次數表示，約略）：

| 步驟 | 做什麼 | 用到 | model / effort | 操作次數（約） |
|---|---|---|---|---|
| 1. 看圖定規格 | 看巴黎屋頂照片：一個開間寬、石柱夾玻璃；先問你寬度、預設用在哪、露台要不要 | 照片 | Opus、high | 約 5 次 |
| 2. 寫尺寸 | 在 `kit_dims.json` 加 `dormer.atelier`（寬、石柱、窗台、窗頂、簷高） | JSON | 同上 | 約 1 次 |
| 3. 寫零件 | `modules.py` 加 `dormer_atelier()`：開口、石柱、石楣、屋頂、鐵框格；加進 `catalog` 和 `openings()` | Blender 腳本 | 同上 | 約 8 次 |
| 4. 建置 | `npm run kit`，看零件數與尺寸檢查有沒有報錯 | 終端機 | — | 約 1 次 |
| 5. 接到網頁端 | `generator.ts` 認得新款式、`plan.ts` 的窗寬、`rooms3d.ts` 的通道大小、`windowEditor.ts` 的選單 | TypeScript | 同上 | 約 5 次 |
| 6. 截圖驗證 | 外面看、切開看室內、點選換款式；檢查有沒有缺面、穿模 | 瀏覽器腳本 | — | 約 5 次（含約 4 張截圖） |
| 7. 平面檢查 | `planCheckAll` 跑全部組合 | 瀏覽器 | — | 約 1 次 |
| 8. 烘焙 AO | `npm run ao`（約 10 分鐘，不花 token） | Blender | — | 0 次（只等待） |
| 9. 文件、commit | 更新 KIT_SPEC、INTERIOR_SPEC，commit | 檔案 | Sonnet 也可 | 約 2 次 |

**你看了之後給的修改（紅線、藍線），再走一輪**：

| 步驟 | 做什麼 | 為什麼多花 |
|---|---|---|
| 10. 讀你的標示 | 紅線：屋頂要傾斜並伸出、不要 90 度；藍線：落地窗、橫桿一條靠上 | 一張標了線的圖，比一段文字省很多 |
| 11. 新增另一款，舊的保留 | 新款 `dormer_studio`，舊款留在選單 | 兩款共用開口輪廓與通道的程式 |
| 12. 連鎖的改動 | 新窗比閣樓矮牆還低 → `rooms3d.ts` 的矮牆也要開洞，通道側牆沿著折線走 | **這是最容易漏的**：外牆零件改了，室內也要跟著改 |
| 13. 再發現問題，再修 | 窗框太暗看不到格子 → 改淺色；屋頂下側牆有缺口 → 側牆頂沿著屋頂底面 | 近看才發現的小事 |
| 14. 再烘焙一次 AO | 形狀變了，AO 要重做 | 如果 12、13 的問題一開始就想清楚，只要烘一次 |

**這個例子的教訓**
-   **新款式一定連鎖**：外牆零件、室內開口、點選範圍、AO、文件，五個地方。事先列出來，就不會漏。
-   **圖上標線最省**：一輪就對了方向。
-   **近看的小缺口，在零件總覽就能發現**：下次先在零件總覽看一圈，再烘焙 AO，可以少烘一次。
-   **舊款保留**：用選單切換，不要刪，改壞了還能退回。

## 11\. 你可能不知道的事

-   **剖切的原理**：three.js 的區域剪裁平面；材質改成雙面，看到背面就塗橘色，**不需要算切口的形狀**，所以匯入的模型也能 剖，前提是網格封閉、法線朝外。
-   **效能看的是「繪製次數」**，不是三角形數：實例化讓同一個零件放幾百次也只有一次繪製；一棟建築約 100 次繪製、3 到 5 萬三 角形，很輕。
-   **光源數量要固定**：每多一盞光，所有材質都變貴；改用固定的小池子，依鏡頭位置分給最近的燈。
-   **細線會在遠處消失**：mipmap 把細線平均掉，被透明度測試丟掉；要用距離提高覆蓋率（欄杆的鐵花就是這樣修的）。
-   **單位與座標**：Blender 是 Z 向上，three.js 是 Y 向上；3D 檔常是毫米。
-   **決定性隨機**：用「種子 + 位置」雜湊，改一個參數不會讓整棟重排。
-   **測試要跑全部組合**：平面規則、尺寸、邊界的錯誤只出現在少數組合。
-   **部署**：分支 `interior-floors` 推送後部署到 `/dev/` 預覽，正式站（main）不受影響。
-   **授權**：現成模型先確認授權再用；照片只取比例與款式，不抄細節，風險最低。

## 13. 尺寸檔如何變成零件（kit_dims.json → Blender）

### 13.1 是什麼

`blender/kit_dims.json` 是整個專案的**尺寸總表**，單位公尺：開間、牆厚、樓高、窗寬、陽台、老虎窗、室內樓板與走廊、樓梯、街道。Blender 腳本與網頁 TypeScript 都從這裡讀，**程式裡不寫死數字**。它不是自動產生的，是人（或 AI）在每個階段需要新尺寸時手動加進去；數字來自照片估出的比例、現實的規範（踏步高度、走廊淨寬）、以及實作時調出來的值。

### 13.2 流程

```
kit_dims.json → build_kit.py → kitlib/*.py → MeshBuilder → Blender 網格 → GLB 與 manifest
   (尺寸)       (讀入、迴圈)   (每個零件一個函式)  (自寫的小工具)  (bpy)        (給網頁用)
```

1. `npm run kit` 啟動沒有介面的 Blender，執行 `build_kit.py`。
2. 腳本用 `json.load` 把尺寸讀成 Python 字典 `D`。
3. `kitlib/modules.py` 的每個函式接收 `D`，用裡面的數字決定形狀。
4. `kitlib/blend.py` 把形狀交給 Blender（`bpy`）變成網格物件、指定材質名稱、展開 UV。
5. `export_kit.py` 匯出 GLB（幾何與材質）與 `kit_manifest.json`（每個零件的資料：包圍盒、開口輪廓、凹槽、三角形數）。

**Blender 不懂 JSON，也不做設計**：它只負責存放網格、指定材質、展開 UV、匯出。形狀的邏輯全在我們的 Python 裡。

**每一步建議用什麼 model 與 effort**（以 Claude 為例，依本專案經驗；以操作次數表示，約略）

| 步驟 | 工作 | 建議 | 操作次數（約） | 說明 |
|---|---|---|---|---|
| 定尺寸 | 看圖、估比例、決定要新增哪些鍵、寫 `_doc` | Opus、high（簡單的改值：Sonnet、medium） | 約 1 到 5 次 | 尺寸影響零件、室內、AO，要想清楚連動 |
| 寫零件 | `modules.py` 的函式，用 `D` 做形狀 | Sonnet、high | 約 8 次 | 有規格、有現成的 `MeshBuilder` 可用；複雜的零件（開口、連動室內）才升 Opus |
| 寫 `MeshBuilder` 這類基礎工具 | 新專案才需要，一次性 | Opus、high | 約 10 到 15 次 | 之後每個零件都靠它，錯了全部連帶 |
| 建置與匯出 | `npm run kit` | 不需要模型 | 約 1 次 | 在你的電腦跑，只讀結果 |
| 尺寸檢查失敗時 | 找哪個零件跑出範圍 | Sonnet、medium | 約 1 次 | 讀錯誤訊息、改尺寸或形狀 |
| 接網頁端 | manifest 開口、排列規則、室內開洞 | Opus、high | 約 5 次 | 連鎖改動，最容易漏 |
| 驗證 | 截圖、零件總覽 | Sonnet、medium | 約 5 次 | 看圖找缺陷；找不出來的疑難才升級 |
| 重烘焙 AO | `npm run ao` | 不需要模型 | 0 次（只等待） | 只有完成後的建置與 commit 才算 |

- **規律**：決定「尺寸與連動」的步驟用 Opus；照規格做形狀與驗證用 Sonnet。
- **其他模型**：依第 11 節的假設（Astra ≈ Opus high、Qwen ≈ Sonnet 5.5）對應；未經第 6 節測試前，這只是推測。

### 13.3 一個零件的例子（老虎窗的玻璃窗洞）

```python
a = D["dormer"]["studio"]                  # 取尺寸：front 2.7、pier 0.2、sill 0.12 ...
gw = a["front"] / 2 - a["pier"]            # 窗洞半寬 = 1.35 - 0.2 = 1.15
loop = P.opening_loop(gw, sill, head)      # 窗洞輪廓：一圈 (x, z) 座標
mb.wall(0, 0, 0, 0, "stone_trim", y=yf, outer=[...], holes=[loop])   # 牆面挖掉這個洞
mb.box((x0, yf - 0.04, 0.0), (x1, yf, zt), "stone_trim")             # 石柱：一個方塊
```

### 13.4 中間的一層：MeshBuilder

- 我們自己寫的小工具（`blender/kitlib/geom.py`），提供 `box`（方塊）、`wall`（牆面加洞）、`sweep`（沿路徑掃出剖面）、`planar`（平面多邊形）、`prism`（擠出）等。
- 先在 Python 裡記下頂點和面，**不碰 Blender**；建完才由 `blend.py` 一次轉成 Blender 網格。
- 好處：形狀邏輯與 Blender 分開，容易檢查與重用。壞處：基本函式要自己寫（本專案階段 A 已寫好）。
- **新專案要先寫這一層**，後面每個零件才便宜。

### 13.5 為什麼用腳本與尺寸檔，不手動建模

- 手動建的零件，改一個尺寸要全部重做；用腳本，改一個數字，所有零件一起重建，也不會互相對不上。
- 零件、室內牆的開口、石縫、AO 都靠同一組數字，窗洞寬度只在一個地方。
- 多人（或多個模型）分工時，大家讀同一份，不會各寫各的數字。

### 13.6 尺寸檢查

建置時，每個零件算出的包圍盒要和規格比對（`catalog()` 裡的 `check`），超出範圍就讓建置報錯中止。擋掉的是「改了 JSON，卻讓零件跑出自己的範圍」這類錯誤。

### 13.7 修改尺寸的流程

1. 改 `kit_dims.json` 的數字。
2. `npm run kit`：腳本重讀、重算形狀、重新匯出。
3. 網頁重新整理，看到新零件。
4. 零件形狀變了，通常也要重烘焙 AO（第 4 節）。

**規矩**：尺寸只改這裡；改了和零件有關的數字，要重建 kit；新尺寸要加 `_doc` 說明單位與意義。
