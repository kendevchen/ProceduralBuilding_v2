# P8 執行紀錄：正式開放 20 上限

日期：2026-10-08。分支：`feature/room-editor`。Model／effort：GPT-6.1 Sol / high。

**功能與自動化回歸完成；新介面瀏覽器操作／視覺驗收尚未完成。** 使用者明確選擇「先完成 P8，開放 20 上限並保留效能限制說明」，因此未將 P7 的 100／300 ms 門檻當作阻止開放的條件。未推送或部署。

## 1. 主介面、尺寸與候選提交

三個滑桿的上限由 `kit_dims.json` 讀取 20，正面／側面最小 2、上層最小 1，全部整數。20 上層另加一樓、閣樓，共 22 個實際樓層；除錯樓層滑桿跟隨平面資料。

新增「平面配置：自動／中庭／採光井」。`defaultInteractiveParams()` 只改主介面預設為 `bays-v2`／`auto`，原 `defaultParams()` API 不改。完整預設與舊 10×8×6 的新版 auto 平面均與 legacy 相同；舊矩陣入口明確固定 legacy 尺寸及模式，不受目前 GUI 模式影響。

新連棟以側面開間控制進深，保留「連棟尺寸：按側面開間／相容公尺」及精確 `depth` 欄位，相容模式停用側面開間；回歸確認 `12.345678 m` 原值保留。大型戶數標籤依解析模式改為「每個核心戶數」，舊配置仍為「每層戶數」。

`BuildingPipeline.prepare()` 在快取與編輯重套之前檢查生成平面 issues。`PlanFeasibilityError` 保存完整原因；GUI 失敗時復原最後成功參數、更新滑桿／選單及模式摘要，再顯示錯誤，不先處置原模型。按棟保存最後成功參數，切棟取消未提交工作。新增基本設定先複製模式／尺寸版本、換種子、清空窗戶覆寫，以新 pipeline／RoomEdits 預檢成功後才新增棟群。生成候選失敗不改原編輯版本、current 平面及快取計數，仍可復原原房型。

## 2. 尺寸掃描發現及處理

完整尺寸軸：正面 `[2,3,5,7,10,11,14,20]`、側面 `[2,3,5,8,9,12,16,20]`、上層 `[1,2,4,6,7,14,15,20]`，獨棟 auto、seed 1，共 512 組。此為公開範圍觀測，與事先明列的 ready／infeasible 指定案例分開。

第一次掃描有 29 組 checker 問題：未開多樣性時，一條房間邊緣相鄰不同牆厚，原本取整邊最大牆厚內縮，令薄牆門洞離開輪廓。P8 將逐牆段內縮套用於所有非公共／設備房間，並新增 11×9×14、14×20×14 指定回歸。門口、有效樓梯連接問題消失，五組候選由不合格轉為合法。

最終分類：**211 組生成平面通過、277 組結構試排即不可行、24 組最終取樣路徑超過配置的 45／50 m**。24 組不是幾何錯誤的任意預期分類：CLI 只容許精確匹配已設定路徑限制的 checker 訊息，逐組確認主介面 pipeline 會拋出相同 issues 並保留原平面／編輯／快取；其他 checker 問題仍使檢查失敗。指定的 ready 案例不得因任何問題改分類。

路徑超限代表現行候選不可提交，未宣稱基地在所有其他設計下都不可能。沒有放寬路徑門檻、把設備井當通行門，或把走不到的房間改成公共廊。每組設定／模式／尺寸／房間數／原因與時間見 [P8上限檢查.json](P8上限檢查.json)：重現參數為 `baseParams` 加該列 `overrides`。其中毫秒是一般回歸耗時，不是正式 5 暖機／30 樣本效能基準。

## 3. 高層鏡頭與展開

歸位使用實際世界包圍盒投影框景。展開先驗證固定展示鏡頭是否能框住全部角點，放不下則依目前相機 FOV／長寬比計算完整框景；建築世界位置及陰影範圍沿用實際 bounds。`cameraFrame.ts` 由獨立 Three.js 相機投影驗證四種長寬比、三種尺度與非零位置，共 96 個角點。

展開自動切線除樓梯外也避讓全棟電梯廳／電梯／管道井。保留安全軸不足時的比例分段與手動剖切。17 種展開回歸包含世界座標核心避讓、室內／孔洞、shader／材質、燈光、點選、21285 個可保留房名及釋放檢查。
