## 1. 交付範圍與規劃預設

目標是正面開間 `baysX`、側面開間 `baysY`、上層數 `floors` 的 GUI 上限皆為 20，並能產生與顯示合理的大型建築平面。

**樓層語意沿用目前程式：20 個上層 = 2F–21F，加 1F 與閣樓，共 22 層。** 不在這次把 `floors` 改成含一樓的總層數。

### 1.1 已確定的方向

- 三個上限都擴大，包含垂直到 20 個上層。
- 依原提案分階段完成平面、垂直動線、採光空間、3D 及檢查。
- 小建築保留既有結構格子、樓梯與走廊配置；樓層多樣性可以改變房間用途、合併與室內細分。
- 保留房間編輯／復原、窗戶設定、多棟建築、剖切、展開、材質及家具功能。
- 所有尺寸與門檻集中於 `blender/kit_dims.json`；文件用繁體中文。

### 1.2 尚待使用者選擇，草案暫採的值

下列是規劃假設，**不是已取得的使用者決定**；已在對話提出選項，回覆後更新本表。

### 1.3 其餘建議預設

- 中庭先支援 O 形及可行的 U 形；L 形另列後續。
- 高層的禮儀大樓梯在入口核心只做 1F→2F；持續向上的必要樓梯另外保留。低層原有主樓梯不變。
- 不以「剪刀梯」名稱代替兩座真實樓梯的幾何與路徑；首版採兩座可辨識的梯段／井道。
- V3 接待室合併與 V4 臥室合併初始機率各 30%；有中庭時 W4 先採對稱。
- 中庭與採光井均貫穿至屋頂；屋頂、樓板、閣樓必須有實際開口。
- 逃生相關數值先作生成器的可調幾何規則，不宣稱法規認證。一般路徑上限可用原提案 50 m 作起點，高層更短的值在 P3 尺寸試算後固定；若另要求真實法規，再指定地區查證。
- 新空間先有幾何、門、名稱與三種材質模式；不把新家具造型、電梯運行動畫納入首版。

## 3. 先修正原提案中的規格缺口

### 3.1 舊範圍與 20 m 門檻

現行獨棟 10×8 室內進深為 25.2 m，已超過提案的 20 m 中庭門檻。

規劃採以下優先順序：

1. 自動模式且仍在舊尺寸範圍、上層數 ≤6：走既有結構配置。
2. 超出舊範圍：依寬、深、高與採光面共同選配置，不只判斷進深。
3. 使用者明確選中庭或採光井時，進入相應配置可行性檢查；不默默改成別種模式。

「保留」指結構格子／樓梯／走廊。開啟樓層多樣性後，房型與合併結果可以不同；多樣性關閉時，舊場景應與基準一致。既有連棟使用公尺的資料須另保留 legacy 尺寸路徑。

### 3.2 中庭不是所有深平面都放得下

- O 形必須同時驗證總寬、總深、各翼寬、核心與中庭淨尺寸；中庭短邊初始要求 `max(6 m, 0.5 × 牆頂高度)`。
- U 形拿掉後翼只增加一個方向的空間，不能解決基地太窄。街角背面是盲牆時，也不能把其背面出口當成對外通道。
- 自動模式依序嘗試 O、允許且可行的 U、採光井配置。候選全部不可行時回報原因。
- 兩端單排／狹長配置納入候選可行性，窗間壁、動線與房間最小尺寸是硬條件。不得為了湊形狀產生負尺寸或把走廊畫穿房間。

### 3.3 採光井的組數與尺寸要一起解

- 原式 `n = floor((D − 11.25)/(W + 10.05))` 只能當初始估算；`n` 是「內部組＋背面組」總數。不能在空間不夠時強制至少 1。
- 20 上層牆頂 68.4 m，`0.1H = 6.84 m`；若對齊 3 m 間距的窗間壁，所需井列可能增至 9 m，不能先把 W 寫成 6 m 再宣稱符合高度規則。
- 枚舉可行組數、井列深度及房間帶深度，對齊後重新驗證所有淨尺寸。剩餘深度不得為負；容納不下時退到較少組數或另一個可行候選。
- 原提案「60 m 高層可排三個附加組」改為試算結果，不列為強制驗收數。低層 10×20 能有至少兩個內部組的指定場景仍需驗證。
- 井間距與加寬後的井共同排程，先扣掉核心與連通走廊，再核對所有房間帶的實際窗面。不能只依「每三個開間一井」推論整排都有窗。

### 3.4 樓梯與公共路徑

- 樓梯需求由實際樓層／服務範圍決定；正面 ≤10 不能在高層時一律只保留一座梯。
- 7–14 個上層：每戶可經公共動線到兩座不同的有效樓梯，核心有電梯。15–20 個上層依原提案配置更完整的雙梯／雙電梯核心，尺寸由實際幾何試排，不把 2 開間×7–8 m 當成已證實足夠。
- 兩座梯各自必須能連續走到一樓的實際對外出口；不能把只有 1F→2F 的禮儀梯算作高樓層第二梯，也不能把同一座梯的不同樓層算兩座。
- 公共走廊、電梯廳與戶內通道分清楚。前往另一核心不能穿過別戶客廳、店面或電梯井。

### 3.5 多樣性規則衝突

- V6 戶型模板依垂直分段固定；D1 每層抽模板與此衝突。首版 D1 改為「每段、每組」抽模板，組內 V1–V5 每層變化。
- W1 大戶翼、W2 轉角跨翼及 D3 跨組合戶會影響分戶：也依分段決定；W3 房型偏好每層可變，W4 對稱每段固定。保留跨段至少兩種 W1 結果的驗收。
- 簽章只比較幾何與用途，排除 `3F-01` 這類含樓層名稱的 ID、樓高、原始 apartment 編號及隨機種子。戶與合併群組依所含格子重新正規化。
- 由下往上生成，與「前一個實際相鄰樓層」比較，不跨越豁免樓層。宴會廳／挑空以外的可變區域才參與其對應的多樣性判定。
- 最多重抽 8 次；無合法不同方案時記 diagnostics，不放進幾何錯誤 `issues`。指定的大型驗收場景必須無未解釋重複；一般小建築可按豁免規則重複。

### 3.6 採光與空間類型

「每個房間都有窗」落實為：客廳、臥室、書房、閣樓居室等需要採光的房型必須有有效窗；廁所、浴室、衣帽間、玄關、儲藏與設備空間可以無窗。廚房遵守既有允許條件並優先臨窗／管道間。

所有實際立面開口須有唯一歸屬，包含中庭與井窗。電梯／設備井設維護或設備開口語意，不列為可以穿越的住戶房間。室外中庭、井、露台不假裝成 `storage` 房間。

深平面的無窗比例在 `program` 分配前，依結構預先標記的住宅可用格計算；目標 ≤10%，並另報服務空間面積。不能事後把無窗格全改名儲藏間來通過比例檢查。

## 4. 資料結構與生成流程

### 4.1 共用結構資料

建議新增 `src/buildingTopology.ts`，保存純資料及解析入口；平面內部演算法按責任逐步移入 `src/planning/`，不要一次搬動整份 `plan.ts`。

| 資料 | 必要資訊／責任 |
|---|---|
| `BuildingTopology` | 參數版本、解析後尺寸／樓層、配置模式、區域、立面、核心、孔洞與固定格子 |
| `BoundaryLoop / FacadeSegment` | 穩定 ID、外側／中庭／井／盲牆、端點、朝向、開間及可開窗區間 |
| `Wing / Module` | 穩定 ID、局部座標系、單排／雙排分區、可用採光面；轉角格只有一個擁有者 |
| `PlanCell / Subcell` | 不含樓層的結構格 ID、區域、幾何、鄰接；細分另有局部 ID |
| `Core` | ID、位置與朝向、服務樓層、樓梯 ID、電梯／廳／管道井、平台開門邊 |
| `VoidVolume` | 中庭、井、電梯井、管道井、宴會廳各自類型與起訖高度／樓層 |
| `Apartment / CirculationGraph` | 每層戶別、所屬核心／組／翼、出入口、公共／戶內通道、門與有效樓梯連結 |
| `PlanDiagnostics` | 解析模式／退回原因、重抽與重複樓層、耗時、不可行原因；與 `issues` 分開 |

相容做法：保留既有公開 `BuildingPlan` 房間／牆／門窗陣列，漸進增加結構資訊。`PlanStair` 的 `kind` 繼續表示造型，另加獨立 `id`、`coreId`、朝向及服務樓層，不能再以 `main/service` 當唯一鍵。

外部四面仍維持現有 `side` 與 `windowKey` 識別。內側立面新增穩定 `facadeId`／opening key，透過統一查詢解析；不可重新編外側窗號，導致個別設定轉移。拓撲改變後消失的內側窗設定需暫停或失效，不套到其他井窗。

### 4.2 新資料流

```text
BuildingParams → 正規化尺寸／版本／樓層
               → resolveBuildingTopology（一次：區域、格子、核心、孔洞、入口）
               → generateBuilding（外側＋內側立面與實際開口）
               → planBuilding（各層分戶、program、細分、開門、簽章）
               → checkPlan ＋ diagnostics
               → 套用房間編輯，再檢查編輯後平面
               → 平面檢視／屋頂與外牆／室內與家具／剖切與展開
```

核心、孔洞不能等外牆生完後才由平面臨時決定。預留結構與外牆共用一份資料，避免雙向重算或不同模組各自推算出不同位置。

小建築先透過舊路徑轉接共用介面，以結構快照驗證結果。每個階段都保留可編譯、可執行的入口。

### 4.3 幾何實作界線

- 中庭／井是平面區域的扣除空間；房間不可跨過孔洞。L 形戶由多個正常房間組成，避免把跨翼戶全部包成矩形大房間。
- 翼的分區、樓梯與門在局部座標生成，再轉回建築座標；不能讓右／左翼的梯仍只朝全域正面開平台門。
- 樓板與天花使用區域外輪廓＋孔洞，包含井道側壁與切口。U 形使用凹外輪廓，不把碰到外邊界的開口當封閉 hole。
- 屋頂改用共享 `RoofPatch`／屋頂區域：外側保留既有孟莎語彙，內側先用垂直內牆與收邊，對中庭／井保留通天開口。區塊接縫不重疊、不漏面；不能對整個 O／U 形直接用現有凸輪廓內縮。
- `atticCeiling` 改為依所屬屋頂區域查詢，否則套用所有翼的屋面半平面會錯誤壓低其他翼的家具。
- 優先重用 `court`／背立面零件。只有實際修改零件形狀時才走 Blender→manifest→AO 流程；若只是重排現有件，不預先要求重烘 AO。

### 各階段的重要限制

- P0 先把平面矩陣抽成獨立入口，避免 `check:rooms` 前面的合併失敗使整個矩陣根本沒執行。
- P1 先作效能試算與幾何介面的小型驗證；確認棟級／層級資料責任後，才實作新配置。正式 GUI 不在此時拉到 14 或 20。
- P2 每次抽樣都從不可變結構重新建立當層單位，避免重抽殘留合併、開門或窗戶歸屬。細分後保留必要採光與可達性；不能在 5 m 深臥室硬切浴室後留下不足最小尺寸的床區。
- P3 公共走廊預留先於分戶；每個核心 1／2 戶的強制選項仍受幾何可行性制約，並回報實際戶數及退回原因。宴會廳的「一戶」只作用在其所在服務區，不能強迫大型整層變成一戶。
- P4 可分為內部資料驗證與 3D 收尾兩次提交，但尚未做真實井窗與屋頂洞前，不在 GUI 公開為完成配置。
- P5 入口門廊是有頂的 1F 通道，上層保留前翼房間；不得將整個前翼垂直挖空。各核心有到入口／街道的公共路徑。
- P6 的 A/B/C 先驗證客廳、廚房、廁所與至少一間臥室的容量；V4 合併不能吃掉最後必要臥室。A、C 不可行時回 B；B 也不可行才用明確的緊湊戶或回報不可行。
- 若首版納入設備層／退縮露台，增加 **P6b**：逐層外輪廓、立面段、露台欄杆、樓板及屋頂邊界，樓層總數不額外增加。核心／管道仍連續，層高改變須由共用樓層表驅動。建議 Astra / xhigh。

## 6. 驗收設計

### 6.1 必須新增的硬檢查

1. **幾何**：房間有正面積、不重疊、不侵入井／中庭／核心保留區；門洞在共牆內，兩側參照一致；住宅房型淨尺寸符合設定。
2. **開口**：每個實際窗與立面開口唯一歸屬、房間與窗雙向參照一致；窗間壁對齊涵蓋外立面及內側立面；盲牆沒有假窗。
3. **公共與戶內通行**：單戶內所有正常使用空間可到出口，公共廊可到有效核心；不可穿過另一戶、井道或屋頂孔洞。
4. **垂直連通**：每座必要樓梯平台、梯段、各層門及底層對外門真正連通；高層每戶可到兩個不同 `stairId`。電梯不計入樓梯逃生路徑。
5. **距離**：使用帶長度的門／通道圖與房間內可行路徑，不能只以房間中心直線距離或房間 hop 數代替。L 形與凹房間的路徑不可穿牆；最遠點取樣與精確計算範圍要在報告說明。
6. **上下對齊**：核心、井道、中庭／採光井、固定格界一致；接觸立面的牆只可選擇移除，不能新增不在結構格界的接點。內部細分不碰立面。
7. **深平面**：每條走廊接到核心；端欄到最近走廊最多穿過同戶的一間其他房間；無窗住宅可用格比例符合 3.6。
8. **3D 一致**：井、中庭及設備井對應正確的樓板／天花／屋頂開口，無封頂、錯向牆或穿洞家具；U 形凹角與屋頂接縫正確。
9. **可重現**：同一輸入結果一致，候選排序不依 Map 遍歷偶然順序；重抽不污染其他層／戶；只改材質或窗扇角度不重排平面。
10. **房間編輯**：合併後開口參照與通行仍正確；結構房型不可改成臥室來解除保護；改參數後不相容操作暫停，切回可以重套。

### 6.2 矩陣拆法

- **舊配置組**：保留原 25,920 組（種子 1／2／3、auto／one／two），先以舊模式驗證，再針對開啟多樣性的代表場景測新行為。
- **快速組**：明列固定案例與門檻前後，不直接取全部笛卡兒積。涵蓋正面 10→11、側面 8→9、上層 6→7、14→15、20；寬深極端 2×20、20×2、2×2；有／無中庭、兩種轉角、三種建築、兩種樓高配置、宴會廳兩種立面、三種一樓用途。
- **完整組**：正面包含 2、3、5、7、10、11、14、20，側面包含 2、3、5、8、9、12、16、20，上層包含 1、2、4、6、7、14、15、20；以分批輸出執行，保留種子、配置、耗時與重現命令。可行／不可行的預期分類分開統計。
- **連棟**：新的 bay 驅動尺寸及舊 `depth` 相容入口分別測試；不能寫 `baysY:16` 卻實際仍測 12 m 深。
- **失敗不能吞掉**：必須支持的指定場景回傳不可行即失敗。極小基地只有在預先定義的限制案例中可預期回報不可行，不能把任意壞配置都改標不可行來使矩陣全過。

### 6.3 指定場景（種子 1–10）

| 場景 | 主要要求 |

### 6.4 每階段與交付檢查

- 每個有程式改動的階段：`npx tsc --noEmit -p .`、`npm run build`、相應快速矩陣與舊模式回歸。
- 平面規則階段交付：`window.__app.planCheckAll([1,2,3],["auto"])`、`["two"]`、`["one"]` 各跑一次；獨立 CLI 必須與瀏覽器共用相同場景來源與 checker。

- 瀏覽器使用測試埠 5177，保留使用者的 5176。只截必要的平面、頂視孔洞、核心剖面與展開畫面，並實際測試拖拉、切棟、改房型、復原。
- 自動幾何通過不取代瀏覽器畫面確認；若視覺／效能驗收未做，狀態中要明確列為未完成。

## 7. 效能與互動策略

### 7.1 量測口徑

- 平面目標：20×20×20 的結構解析、當層規劃與硬檢查合計，預熱後 p95 ≤100 ms。不能把檢查移出計時後聲稱達標。
- 完整幾何目標：外觀＋平面＋室內＋家具的 CPU 重建 p95 ≤300 ms，GPU 首次編譯／上傳另列。若未達，記錄分項瓶頸與實測值，不能拿局部樓層時間替代整棟時間。
- 固定瀏覽器、視窗、pixel ratio、陰影／後製與硬體，至少 5 次暖機、30 次樣本，記錄 p50／p95、房間數、三角形、draw calls、幾何記憶體；冷啟動另列。
- 家具成本高於平面：P1 的 20×20×20 寫實試算，家具 p50 約 12.9 秒；室內／樓梯／家具約 1,244 萬面、974 MiB buffers，標籤 RGBA 基礎貼圖估算 808 MiB，室內展開另加 199 MiB buffers。P7 必須處理家具生成與幾何共用、標籤配置及展開成本，再驗證瀏覽器整合；100／300 ms 仍是待驗證的目標，不可只以純平面達標代替。詳見 P1 原始量測及 scope。

### 7.2 實作順序

1. 格子相鄰、窗到格、房間到牆建立索引；`connect` 使用鄰接表與增量 BFS；`checkPlan` 同樣使用索引，避免仍在 checker 留下平方級掃描。
2. 窗到格共用幾何映射，各層仍套自己的有效開口集合：老虎窗、宴會廳高窗、1F 門廊與店面不能共用錯誤歸屬。
3. 快取分為結構、各層生成平面、編輯後平面、幾何，key 包含有影響的參數／版本。窗扇角度／材質只更新相關外觀；老虎窗有無與開口形狀要更新採光與對應平面。
4. 滑桿拖動可節流顯示外形，提交時做一次完整解析；外觀預覽不讀取舊平面當新窗景，使用暫時相容預覽資料。不可在每個 `onChange` 都重建整棟家具。
5. 保留只建目前棟室內的策略；室內幾何仍依材質合併，對可重用家具採共用幾何／必要的實例化，不擅自刪家具或降低既有造型品質。
6. 若首度顯示仍卡住，可分層排程、先顯示可見樓層，再補其餘層；有 generation token 取消舊任務，避免切棟後塞回舊家具。此策略另報首屏與全棟完成時間，不冒充整棟 300 ms。
7. 必要時才把純資料規劃放 Worker；Worker 是改善主執行緒阻塞的手段，不代表總運算時間達到 100 ms。
