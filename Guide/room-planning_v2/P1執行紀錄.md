# 20 上限 P1：執行與交接

日期：2026-10-07。狀態：P1 完成；GUI 上限仍為 10／8／6，P2–P8 尚未實作。

依據：[20上限實作計畫.md](20上限實作計畫.md) 的 P1。執行建議：GPT-6.1 Sol / high。

## 1. 共用結構與責任

- 新增 `src/buildingTopology.ts`：尺寸／版本／樓層、外輪廓與邊、四面及斜切立面、固定格子／鄰接、模組、主／服務核心與宴會廳孔洞。資料不含可變房型；JSON 可序列化，解析完成後遞迴 freeze。
- 既有格子／分區／樓梯位置演算法移入 `src/planning/legacyGrid.ts`，保持原計算與排序；外牆生成前就建立。`generateBuilding` 每次只解析一次結構，`Building.topology` 與後續平面共用同一份。原公開 `upperRows`、`ballroomBays` 仍從 generator 重匯出。
- `planBuilding` 只從實際外牆讀取 ground／dormer 開口款式；固定幾何來自拓撲，每層建立自己的 Unit、用途與門。公開平面的內縮輪廓另複製，避免把不可變拓撲交給房間編輯修改。
- 結構 cell ID 不含樓層（`legacy:block:cell:N`），核心／模組／外側立面／斜切面另有 ID；核心服務範圍包含實際閣樓終點差異。宴會廳孔洞只標記 3F 的上半層，Z 範圍與實際平面層一致。
- 外側 `side`、bay、`windowKey`、房間／牆／門窗陣列及排序保留。新中庭／井／多核心、電梯與新房型尚未加入；P1 不增加隨機決策，沿用原 rng streams。

## 2. 尺寸與模式 API

`defaultParams()` 沒有加入新欄位；舊輸入及 GUI 預設保持原路徑。

| 輸入 | 行為 |
|---|---|
| `dimensionVersion` 未填或 `legacy` | 連棟用原 `depth` 公尺值，`baysY` 不改長度；例如 12.345 m 仍是 12.345 m |
| `dimensionVersion: "bays-v2"` | 連棟才改用側面間數：`bay × baysY + 兩端角柱餘量`；20 間為 61 m，`depth` 不參與解析 |
| `layoutMode` 未填或 `legacy` | 既有演算法；超出舊 envelope 的試算加 diagnostics，不代表新採光／高層驗收通過 |
| `layoutMode: "auto"`，仍在舊 envelope | 保留舊結構；包含舊 10×8 本就超過 20 m 進深的相容例外 |
| 大型 `auto`／明選 `courtyard` 或 `lightwell` | 目前為 `unsupported`；尚待 P3–P5 的求解，不能默默轉成 legacy，也不誤稱已證實幾何不可行 |

`resolveBuildingTopology(params)` 回傳 `ready/topology`、`unsupported/diagnostics` 或 `infeasible/diagnostics`。非法結構參數或失效的外牆內縮輪廓為 infeasible；API 不隱性 clamp／四捨五入。API 邊界為正面／側面 2–20 整數、上層 1–20 整數；20 個上層加一樓與閣樓共 22 層。門檻集中在 `kit_dims.json` 的 `interior.planning`；未改零件形狀，不需重建 kit／AO。

`generateBuilding` 遇到非 ready 結果會拋出帶完整結果的 `TopologyResolutionError`。P8 的 GUI 必須先解析、確認 ready 才換掉模型；P1 沒有提供新模式 UI，也還未實作「保留上一個有效模型」的 UI 流程。自動候選的 O／U／井可行性檢查仍是後續工作。

## 3. 索引

- `planning/edgeIndex.ts` 以矩形邊座標分桶，查相對邊及相鄰桶；最後仍用原始座標／容差與有效共邊長度判斷。輸出依原 i／j、垂直／水平順序，維持牆順序及開門 tie-break。部分共邊、細分矩形和挑空可用同一入口。
- connect 的牆／鄰居依 Unit 與 pair 索引，不再反覆掃全層牆；每次開門增量擴張已可達集合，候選優先順序不變。
- 房間牆與門歸屬依 Unit 查表；窗戶按樓層、開間與固定 probe 的格子候選查表。probe 落在邊界時保留原格子順序，遇到宴會廳挑空仍可找下一個有效候選。
- checker 的窗依樓層／內縮邊、房間依層索引，保留原問題順序及 P0 的實際街面入口判定。

## 5. CPU 與幾何基線

環境：Apple M3 Pro、macOS arm64、Node v25.2.1、Vite SSR。下列是此機此輪試算，不能當作所有瀏覽器的時間保證。

### 5.1 結構＋平面

指令：`npm run bench:plans -- --json Guide/room-planning_v2/P1平面效能基線.json`。每場景暖機 5 次／取樣 30 次；generate 已包含新拓撲解析與固定格子，PartIndex 僅回傳 key；plan 含 checker。每個樣本的平面雜湊也核對一致。原始資料：[P1平面效能基線.json](P1平面效能基線.json)。

| 場景 | 房間 | 結構／生成 p95 ms | 平面含 checker p95 ms | 合計 p95 ms |
|---|---:|---:|---:|---:|
| 預設 5×3×4 | 78 | 0.787 | 1.488 | 1.930 |
| 舊上限 10×8×6 | 428 | 2.245 | 8.215 | 9.193 |
| 20×20×20 舊演算法試算 | 2587 | 7.553 | 38.950 | 46.503 |
| 2×2×20 舊演算法試算 | 66 | 0.792 | 2.676 | 3.489 |
| 連棟、側面 20 但舊 depth=12 m | 240 | 1.807 | 3.828 | 4.399 |
| 連棟 20、depth=60 m、上層 20 | 1883 | 4.461 | 23.605 | 26.630 |

P0 同範圍 20×20×20 的合計 p95 為 265.290 ms。這一階段只證實舊演算法試算中的純結構／平面改善，尚不涵蓋新多核心／採光井／中庭，也不涵蓋室內／家具／GPU。

### 5.2 寫實室內／家具／標籤物件／室內展開

指令：`npm run bench:interior -- --json Guide/room-planning_v2/P1室內效能基線.json`。本地 GLB 包圍盒及 manifest 開口，實際執行 production 寫實幾何與配置函式；每場景暖機 1 次／取樣 3 次，GC 在計時外。3 個樣本的 p95 是最大樣本，屬成本量級試算。原始資料：[P1室內效能基線.json](P1室內效能基線.json)。

| 場景 | 室內 p50 ms | 家具 p50 ms | 室內展開 p50 ms | 各階段合計 p95 ms |
|---|---:|---:|---:|---:|
| 預設 5×3×4 | 15.104 | 300.069 | 67.596 | 466.375 |
| 舊上限 10×8×6 | 62.432 | 1275.670 | 263.632 | 1756.292 |
| 20×20×20 舊演算法試算 | 319.583 | 12873.397 | 2629.854 | 16124.090 |

合計包含結構／平面／材質建立、室內、樓梯、家具、標籤物件及室內展開。**不含**資產／module 載入、真正 Canvas 畫圖／字型光柵化、外牆 mesh 實例化、GPU 上傳／繪製及瀏覽器互動；沒有外牆的展開不能代表完整建築的展開量。

| 場景 | 室內＋樓梯＋家具面數 | 原始幾何 buffers MiB | 展開額外 buffers MiB | 標籤 RGBA 基礎貼圖估算 MiB |
|---|---:|---:|---:|---:|
| 預設 5×3×4 | 421,147 | 38.98 | 7.51 | 24.38 |
| 舊上限 10×8×6 | 1,843,276 | 158.68 | 30.42 | 133.75 |
| 20×20×20 舊演算法試算 | 12,440,606 | 974.35 | 198.84 | 808.44 |

buffers 計算唯一 ArrayBuffer，展開只計新增且未由原模型持有的 buffers。標籤是每房一張 512×160、RGBA 4 bytes 的估算，不是實測 GPU 記憶體，也未包含 mipmaps、家具圖像／噪聲貼圖與外牆。process memory 僅記錄建構後快照，不當峰值或 GPU 用量。

家具與標籤／展開成本仍很高；整棟 100／300 ms 目標尚未通過。P7 需要處理家具配置掃描、幾何共用／生成排程、標籤與展開成本，再於瀏覽器驗證；不能以只生成當前層或省略家具後的時間冒充「完整重建」驗收。

## 6. 下一階段

P2：現有範圍的 V1–V5 樓層變化、格內細分、簽章與最多 8 次重抽。建議 **GPT-6.1 Sol / high**。

- 共用拓撲及固定格子保持不可變；新 Unit／subcell／每層用途與重試各自擁有資料。簽章須排除樓層 ID、Z、原始戶號與 seed，按結構 cell／subcell 正規化。
