# 大型建築空間配置調整與模型交接計畫

日期：2026-10-07

狀態：**僅規劃及備份，尚未實作新的房間配置規則。**

後續更新：使用者要求選擇性退回 `2436899`，目前 GUI 上限已恢復正面 10、側面 8、上層 6；保留四向新增、鏡頭動畫及全街區間距。以下 20×20 說明記錄 `f0ec2b2` 的歷史基線與未來方案，不表示目前仍開放 20 上限。備份維持原始內容，勿因本文件自行重新開放上限或啟動大型配置改版。

## 1. 接手目標與基線

專案為 Three.js 程序化歐式建築，工作分支 `feature/room-editor`。

本計畫與備份的歷史基線 commit：`f0ec2b2aae6e592133ef81fa986f25be2351ac66`；目前選擇性回退提交為 `1705615`。

歷史基線已支援多棟建築、四向新增、棟間距、鏡頭切換動畫、獨立房型編輯與剖切／展開；當時正面開間、側面開間及上層數的 GUI 上限提高至 20。目前保留上述功能，但上限恢復為 10／8／6。**房間規劃器仍沿用原本小型建築的規則**，本計畫記錄未來大尺寸適應方案。

這裡的「上一版規劃程式碼」指上述 commit 中、尚未套用本計畫的規劃器；已核對 `2436899..f0ec2b2` 的 `plan.ts`、`generator.ts`、`params.ts`、`rng.ts`、`roomEdits.ts` 與 `kit_dims.json` 沒有改動。即上限擴充前後，這些規劃核心相同。

備份：[原規劃器程式碼快照](./room-planning-v1-f0ec2b2.tar.gz)。完整檔案範圍、校驗與使用方式見 [備份說明](./README.md)。快照未包含模型、貼圖、node_modules 或使用者尚未提交的變更；不是可單独部署的完整專案。

## 2. 使用者期待

- 保留原本初始建築的配置與外觀。
- 大開間、多樓層建築應有更多合理的住宅組合與房型分布，不應只增加臥室、儲藏間。
- 隨機種子應影響住宅配置組合，而不只是交换少數房間的位置。
- 一樓、閣樓既有特殊用途先保留；優先調整一般住宅樓層。
- 不因本工作破壞多棟獨立控制、房間編輯／復原、家具、剖面、展開與相機。

## 3. 原本規則及診斷證據

| 項目 | 原本實作 |
|---|---|
| 分戶 | `auto` 依正面開間門檻決定一戶或左右兩戶；特殊樓層有例外，最多兩戶 |
| 客廳 | 每戶通常一間，優先正面中央；較大格局合併兩個相鄰格子 |
| 廚房 | 每戶通常一間，優先後方、服務樓梯附近 |
| 廁所 | 每戶通常一間，優先無窗位置，再選後方；過大的無窗廁所可分出儲藏間 |
| 臥室 | 先保留一間安靜有窗房間；剩餘未分配的有窗格全部成為臥室 |
| 餐廳 | 房間數足夠，且客廳旁有合適正面房間才配置；二樓另有空間位置導向的餐廳樣板規則 |
| 書房 | 符合樓層／房間數條件才配置；種子 1 保留固定轉角偏好，其他种子一般樓層可從剩餘有窗房間選 |
| 儲藏間 | 未分配的無窗空間預設全部成為儲藏間 |
| 樓層差異 | 標準中間層沿用同一分配程序；20 個上層中有 18 個標準層 |
| 隨機 | 部分候選房間用種子、樓層、戶別、用途選取；不少候選先經位置排序，只有少量並列候選會隨機 |
| 隔間 | 基本格線上下對齊，主要由窗間壁與固定走廊帶決定；少數房間合併 |
| 閣樓 | 主要為閣樓房、無窗儲藏間，另有書房及廁所，獨立於一般住宅程序 |

實測：獨棟、其他參數採預設，取 4F；種子 1、2 的下列數量一致，但位置可能不同。

| 正面×側面開間／上層 | 臥室 | 儲藏間 | 客廳 | 餐廳 | 書房 | 廚房 | 廁所 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 5×3／4 | 5 | 0 | 1 | 1 | 1 | 1 | 1 |
| 10×8／6 | 21 | 14 | 2 | 2 | 2 | 2 | 2 |
| 20×20／20 | 65 | 34 | 2 | 2 | 2 | 2 | 2 |

根因為「每戶有限的功能房配額＋最多兩戶＋臥室／儲藏間兜底」。上限調整的舊驗收只確認生成及平面無 issues，並未驗證配置多樣性。

程式入口：`src/plan.ts` 的 `program()`（約 616 行）、剩餘房間兜底（約 729 行）、分戶（約 836 行）；行號可能因後續編輯變動，請以函式或註解搜尋。

## 4. 建議調整方案

### 階段一：保護基線並擴充自動分戶

1. 在動手前，記錄 `defaultParams()` 的完整平面、房間形狀／用途、窗戶歸屬與通行資料，建立可重現的比較基線。
2. 精確定義「初始配置保留」的適用參數，不能只用 `seed === 1`：20×20 的種子 1 也需要新規則。預設模型須保留；非預設建築如何進入新模式應集中判斷。
3. `apartments: auto` 根據可居住的有窗面積、入口、走廊與相鄰關係決定戶數，取消最多兩戶的限制。先用 20×20 每層約 4–8 戶作探索範圍，**不是已驗證的固定配額或驗收值**。
4. 分戶結果必須連通，每戶能從公共動線進入；不能只依房間數等分，也不能用無窗中央區面積強行增加住宅戶數。
5. 手動「一戶／兩戶」仍尊重使用者設定。大面積一戶採大宅配置，透過房間合併與面積增加消化空間。

### 階段二：住宅配置樣板與尺度適應

先使用現有房型／家具，不把新家具製作一起納入。

| 樣板 | 建議組成方向，需依可用空間調整 |
|---|---|
| 小家庭 | 1–2 臥室、客餐空間、廚房、廁所 |
| 一般家庭 | 2–3 臥室、客廳、餐廳，可能帶書房 |
| 大家庭 | 3–4 臥室、較大客餐空間、書房、較多廁所 |
| 大宅 | 更大的接待／居住空間、較多合併，降低小房間密度 |

- 先依戶的窗戶、面積、形狀選擇可行樣板，再以固定種子選位置／變體。
- 廚房與廁所維持服務區偏好；臥室、客廳等應具備既有採光條件。
- 餐廳可獨立或與客廳合併。但目前房型是單一枚舉，家具按房型生成；「合併客餐廳」需要明確的資料標記與家具支援，不能單純把兩房合成 `salon` 就宣稱兼具餐廳。可先完成獨立房型樣板，再加入複合空間。
- 房間合併必須保護樓梯、外牆、必要通道，維持窗戶歸屬。沿用既有幾何檢查，不直接隨機刪牆。
- 檢討剩餘空間處理：優先重新分配、調整戶界、擴大相鄰房間或合併儲藏區；避免逐格無條件轉成同一房型。
- 房型比例以可用空間及樣板為基礎，不先硬訂全棟通用百分比；小戶與大宅本來就應不同。

### 階段三：樓層差異與可重現性

- 樓梯、主要結構與必要公共動線保持穩定；樓層差異由住宅樣板組合、房間合併及用途產生。
- 依種子與穩定樓層／空間識別選擇配置，避免以可變房間流水號作為主要隨機來源。
- 對相鄰樓層建立配置簽章，在有多個可行選擇時降低完全重複；小格局只有一種可行配置時允許重複。
- 防重複不能無限重抽。設定有限嘗試及確定性的回退規則，避免改頂層數就讓下方所有樓層連鎖重排。
- 增加樓層時保留既有中間樓層；原頂層轉成標準層等樓層角色改變是合理例外。

## 5. 深進深的限制與另案工作

20×20 會出現很大的無窗中央區。增加戶數或隨機房型無法創造採光，不能把無窗房間直接當成普通臥室來達成多樣性指標。

本階段先改善住宅分戶、合併與服務區配置；仍無法合理利用的區域應被量測及明確記錄，不用改名稱掩蓋問題。

採光中庭／天井另立階段，涉及 footprint、內院立面及窗戶、樓板與屋頂開洞、動線、家具、剖切與展開。**本計畫不代表使用者已授權實作中庭、新房型美術或自由道路系統。**

## 6. 實作切分與接手檔案

先讀本文件、`STATE.md`，再讀 `INTERIOR_SPEC.md` 第 5 節；依任務讀程式，不用掃描整個 repo。

| 工作 | 主要檔案 |
|---|---|
| 原配置規則／通行檢查 | `src/plan.ts` |
| 參數、樓層與建築幾何資料 | `src/params.ts`、`src/generator.ts`、`blender/kit_dims.json` |
| 固定隨機來源 | `src/rng.ts` |
| 房間幾何／手動編輯與重套 | `src/roomGeometry.ts`、`src/roomEdits.ts`、`src/roomEditor.ts` |
| 新規則與多棟狀態整合 | `src/main.ts`、`src/buildingScene.ts` |
| 家具與材質相容性 | `src/furniture.ts`、`src/rooms3d.ts`、`src/finishes.ts` |
| 專用一樓／閣樓配色標記 | `src/cafes.ts`、`src/attics.ts` |
| 回歸 | `scripts/check-room-editor.mjs`、`scripts/check-buildings.mjs`、`scripts/check-unfold.mjs` |

建議分開提交：基線與配置品質量測 → 自動分戶 → 樣板與剩餘空間 → 樓層差異 → 視覺及效能驗收。每步確認結果後再擴展，不一次改寫全部規劃器。

## 7. 驗收條件

### 相容性

- 原始預設配置與基線一致，包含房型、形狀、窗戶及動線，不只房間總數。
- 一樓、閣樓及宴會廳保護規則維持；特殊層不是普通住宅樣板的任意覆蓋目標。
- 手動一戶／兩戶、房型修改、合併、復原／重做與參數變動後重套可用。
- 多棟之間的種子、房間編輯、材質、剖切與展開互相獨立。

### 配置品質

- 測試預設 5×3／4、10×8／6、20×20／20，以及窄而深、寬而淺、街角與連棟。
- 使用固定種子集合（例如 1–10），分開統計「房型数量／面積比例」「戶型組合」「空間位置」，不能把移動房間位置當成戶型多樣性。
- 每戶必要機能及公共入口完整，房間可達、無非預期交疊，窗戶歸屬唯一。
- 記錄剩餘臥室／儲藏間的數量、面積與來源，與本文件數據比較；不得只驗證 `issues.length === 0`。
- 統計相鄰標準層的完全重複率；有可行替代方案時應降低重複，無解則採可解釋回退。
- 比較增加樓層前後既有中間層的穩定性。

### 工程與效能

- 執行 `npm run build`、`npm run check:buildings`、`npm run check:unfold`；涉及規劃器變更時補跑原平面矩陣與新增大尺寸案例。
- `npm run check:rooms` 已有已知基線失敗：`reachability survives a merge`，此前已在舊提交重現。接手者需區分既有問題與新退化，不能把本次失敗全部歸為既有問題。
- 原 `check:buildings` 的 20×20×20 只證明生成／平面檢查可完成，不代表完整家具、FPS 或 GPU 記憶體已通過。
- 瀏覽器檢查至少一個大尺寸普通剖面、一個展開、兩棟切換；量測生成時間、幾何／draw calls、記憶體及幀更新。勿宣稱未量測的效能。
- 保留非目前建築室內按需建立／釋放的機制，避免大尺寸多棟同時持有完整室內。

## 8. 工作區及交接限制

- 使用者偏好精簡溝通、節省 token；先讀指定檔案。
- 尺寸集中在 `blender/kit_dims.json`；素材自製。
- 不關閉使用者的 5176 開發伺服器；測試端口先檢查是否已占用。
- 工作區有既有 `.claude/settings.json` 修改、Guide／archive 文件刪除及未追蹤交接文件。這些屬使用者變更，不復原、不納入本任務提交。
- 不讀不存在的 archive、不重建使用者刪除的舊文件。
- 本文件及備份不代表已開始實作。模型接手後依使用者的新指示進行；先提供具體實作切分，再在授權範圍內執行。
- 功能分支可按既有工作慣例本機提交；推送依使用者指示，不能推 main。
